# 后续维护与迁移路线

## 当前可以做的事

- 按包名阅读与定位，原 JAR、资源和依赖有固定散列。
- 在工作副本修改，并与不变的反编译参考比较。
- 重复执行完整性、源码覆盖与编译诊断。
- 继续用现有 muxi-game-core 实施小范围修复，再运行隔离服测试。

## 完整重建之前需要处理的事

1. 恢复原构建流程中的访问权限处理。包内有 `customnpcs.accesswidener`；普通 javac 不会自动应用它，因而 private/protected/final 错误不都代表原模组逻辑错误。需要为编译依赖生成正确的访问变更，不能改动现有运行目录的 Minecraft JAR。
2. 恢复泛型与重载信息。反编译输出可能丢失显式类型，表现为网络注册方法引用歧义、泛型集合类型不匹配。逐项对照原始字节码确认实际调用描述符。
3. 处理 Mixin 接口转换。目标类型的运行时结构与未注入的编译依赖不同，需要明确桥接或正确的编译环境；不能删除原来的兼容逻辑。
4. 编译通过后，再建立可复现打包、开发构建版本号与客户端/服务端配套验证。本工具故意只做编译检查，不会把未验证的代码制作成可安装 JAR。

## 每项改动如何记录

在 `patches/` 新建说明：问题编号、受影响文件/方法、原始字节码证据、改动理由、行为是否变化、对应回归用例与结果。构建恢复与功能修复分开提交，便于将来迁回作者源码。

原 JAR 中的 BUG 也属于当前行为基线。反编译整理阶段不要悄悄修正它，否则不能判断变化来自恢复误差还是有意修复。

## 获得作者源码后的迁移

先拉取到新目录，确认版本、提交、依赖和许可；构建未修改版本，验证与当前发布包的接口、资源及运行行为。随后按问题编号逐项移植自己的补丁，并重跑原有回归用例。不要用反编译目录覆盖作者源码，也不要将作者源码反向塞进旧参考目录。

任何正式迁移都需要备份世界/NPC 数据、验证旧数据读回及失败回滚。当前阶段仅准备材料和工具，不作架构更换或正式部署决定。
